# 工作目录与交付证据

用于 Seedmux 并行写入、独立审查和主控集成。派发操作仍使用应用提供的 `seedmux-team`；这里规定项目协作的边界，不另建调度器或任务数据库。

## 派发前确定版本

单个执行者的小任务可继续在当前 checkout 工作。多个 agent 同时写代码时，每个写入任务使用独立 worktree 与分支；不能仅靠文件 scope 将共享 checkout 变成隔离环境。只读审查使用固定 commit 的独立 worktree 或固定内容快照，作者继续修改不改变正在审查的输入。

主控先检查目标仓库、当前分支和已有改动。worktree 从明确的 commit 创建，不会自动包含未提交或未跟踪文件。任务需要这些文件时，只带上已核对归属的补丁与必要文件，并记录基线 commit、补丁或文件内容哈希；不能把别人的未提交工作强制提交、stash 或整体复制过去。

使用 Git 自带 worktree 能力；给 Seedmux 的 `--cwd` 指向该任务的绝对目录。复用 pane 时核对其实际 cwd，不向旧目录注入一份声称新目录的工单。

## 工单与回执的关联

将以下信息放在已有 Seedmux 工单和回执中；已有 Issue／白板只引用它们，不重复维护状态：

| 信息 | 用途 |
|---|---|
| 仓库、绝对 cwd、分支与基线 commit | 确认实际工作对象 |
| 必要的未提交输入及内容哈希 | 区分干净基线和工作区快照 |
| 目标、允许路径、可验证完成条件 | 约束执行范围 |
| 已授权交付阶段：补丁／提交／推送／部署 | 确定在哪里结束 |
| 交付 commit，或补丁及必要未跟踪文件的哈希 | 标识被验证的版本 |
| 验证命令、退出码、观察结果与未覆盖部分 | 说明证据支持到哪一步 |

界面截图还应关联被运行的 checkout 与版本；只标 HEAD 却忽略未提交改动不能标识实际画面。纯讨论任务可不建立 Git 交付物，只关联问题、证据和已定／未定决策。

## 收口

`scope` 比较目录在派发前后的变化，不代表作者归属；`accept=ok` 只说明对应验收命令通过。出现他人改动造成的越界时，保留原始回执与差异，按官方回执规则报告归因问题；主控核对或重建隔离基线，不扩大 scope 来抹掉异常。

主控审阅交付差异后按仓库规则整合，验证整合后实际版本的受影响行为。子任务完成不等于主任务已交付，也不自动授权 worker 推送主分支。

停止临时测试进程后再清理自己创建、已完成整合且没有未保存工作或运行依赖的 worktree；仍被 pane 或进程使用时保留并说明。保留用户已有工作区与调试入口。
